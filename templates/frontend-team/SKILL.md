# frontend-team — 셋을 조율한다, 대신 하지 않는다

`fe-architect`·`fe-implementer`·`fe-designer`는 각자 "어떻게 일하는가"만 안다. 누가 무엇을 맡고, 어느
순서로 가고, 어디서 넘기는지는 이 스킬이 원본이다. 어긋나면 이 스킬이 이긴다. 경로·검증 명령·디자인
규칙 문서 같은 프로젝트 사실은 `.ai-harness/docs/frontend.md`의 `## 팀 역할` 절이 정한다.

**규칙의 글자를 어기는 것은 규칙의 정신을 어기는 것이다.** 코드를 고치는 손은 셋 중 하나다.

## 팀

| | `fe-architect` | `fe-implementer` | `fe-designer` |
|---|---|---|---|
| 책임 | 구조·인터페이스·UX 디테일·모션·코드 리뷰 | 요구사항 충족과 연동, 가장 빨리 | 디자인 규칙을 지키는 UI 산출물과 채점 |
| 자리 | 어디든. 3파일 넘으면 스펙 먼저 | 앱 화면·API 레이어 | UI 패키지의 페이지·블록·스토리. 앱 코드는 건드리지 않는다 |
| 결정권 | 추상화·레이어·공용화 | 범위·서버 계약 해석 | 디자인 규칙 해석·점수 |
| 스스로 안 하는 일 | 채점 | 채점 · 추상화 판단 | 추상화 판단 · API 연동 |

`fe-designer`가 없는 프로젝트(디자인 규칙 문서나 UI 패키지가 없다)에서는 UI 산출물도 `fe-implementer`가
만들고, 채점 단계는 건너뛴다. 아래 표에서 `fe-designer` 칸을 `fe-implementer`로 읽는다.

## 라우팅

| 입구 | 스폰 | 보고에 "다음 담당"이 뜨는 조건 → 받는 사람 |
|---|---|---|
| UI가 새로 생기거나 바뀐다 — 기획·시안·이슈 어느 것으로 왔든, "앱에 연결까지"가 붙어 있든 | `fe-designer` | 앱 연결·실데이터·API → `fe-implementer` · 공용화·새 레이어 → `fe-architect` |
| 이미 있는 UI를 앱에 연결, API 연동, 동작 로직 | `fe-implementer` | 연결하다 UI를 고쳤으면 채점 → `fe-designer` · 3파일 넘는 구조, 추상화 → `fe-architect` |
| 버그 첫 시도 | `fe-implementer` | 원인이 구조·모션·타이밍, 또는 같은 버그 두 번째 → `fe-architect` |
| 구조 잡기·쪼개기·컴포넌트 API·"공용으로 뺄까"·어색함·광학 정렬·포커스·모션 | `fe-architect` | 만든 UI의 채점 → `fe-designer` |
| 디자인 점수·피드백 판정 | `fe-designer` | 반영이 구조를 바꾸면 → `fe-architect` |
| 코드 리뷰 | `fe-architect` | `fe-architect` 본인 코드는 하네스 `reviewer`(없으면 사용자) |

사용자가 역할이나 프로젝트가 정한 호칭으로 부르면 표와 무관하게 그 역할이다.

테스트는 그 코드를 만든 역할이 쓴다. 테스트 정책이 TDD면 Red도 같은 역할이 먼저 쓴다 — 테스트만 따로
다른 손에 넘기지 않는다. 층위 판단은 `frontend-testing`이다.

## 조율

1. **분류.** 요청을 표의 입구 하나로 적는다. 기준은 요청의 동사("구현해줘", "붙여줘")가 아니라
   **산출물이 어디에 생기는가**다. UI가 새로 그려지면 첫 스폰은 항상 `fe-designer`이고 "연결까지"는
   다음 담당으로 `fe-implementer`에게 간다. 앱 코드만 바뀌면 `fe-implementer`, 자리보다 구조가 문제면
   `fe-architect`.
2. **스폰.** 프롬프트에 넷을 넣는다: 요구사항 원문(이슈·기획·시안 링크), 대상 파일 경로, 이전 보고의
   "안 한 것"·"확인 필요", 그리고 "보고는 네 파일의 보고 형식대로, 마지막은 다음 담당". 서로 독립인
   일(다른 파일, 다른 입구)은 한 메시지에서 병렬로. 같은 파일을 건드리면 순서대로.
3. **체인.** 보고의 "다음 담당"에 역할이 있으면 그 에이전트를 이어서 스폰한다. 넘길 것을 내가 대신
   만들지 않는다. "없음"이면 멈춘다.
4. **끝.** 다음 담당이 없고, 마지막 보고의 검증 절이 통과이고, `fe-designer`가 만든 것은 `design-audit`
   통과 판정이 있을 때. 셋 중 하나라도 비면 끝이 아니다.
5. **사용자에게 올리는 것.** "규칙 결정 필요"·"렌더 확인 필요"·"요구사항-규칙 충돌"·"서버 계약 질문"은
   에이전트가 풀지 않는다. 모아서 한 번에 묻는다.

하네스 워크플로(`/implement-feature`·`/fix-bug`·`/review`)로 들어온 일이면 Brief 승인·검증·리뷰 루프는
워크플로 그래프가 정하고, 이 스킬은 그 안에서 **누구 손으로 하는가**만 정한다.

## 충돌

| 상황 | 결정 |
|---|---|
| `fe-designer` 채점과 `fe-implementer` 구현이 다르다 | 디자인 규칙 문서가 이긴다. 요구사항을 깎아야 맞으면 사용자에게 |
| 둘이 같은 추상화를 다르게 올렸다 | `fe-architect`가 하나로. 나머지는 되돌린다 |
| 문서와 구현이 다르다 | 구현을 틀렸다고 단정하지 않는다. "규칙 결정 필요"로 사용자에게 |
| 에이전트 둘이 서로 넘기기만 한다 | 산출물 자리로 내가 가른다. 두 번째 왕복에서 |

## 직접 해도 되는 것

한 줄 오타 수정, 질문 답변, 코드 조사, 명령 실행, 커밋·PR. 그 밖의 파일 변경은 아니다.

## 합리화 표

| 핑계 | 실제 |
|---|---|
| "한 파일이라 직접이 빠르다" | 한 파일이 UI 블록이면 채점이 빠진다. 빠른 게 아니라 덜 한 것 |
| "스폰 오버헤드가 크다" | 보고 형식과 검증이 오버헤드에 들어 있다. 직접 하면 그게 빠진다 |
| "내가 이미 파악했다" | 파악한 것을 프롬프트에 넣으면 된다. 손은 넘긴다 |
| "에이전트가 더 못할 것 같다" | 못하면 보고에 드러난다. 그때 다음 담당으로 가른다 |

## 빨간 불

Edit·Write를 열려는 순간 그 파일이 `frontend.md`의 `## 팀 역할`이 적은 앱·UI 패키지 경로 안이면 멈춘다.
이 스킬의 표로 돌아간다.
