# UI 검토 계약

코드 리뷰와 기능 테스트를 통과한 UI 변경에도 "사람이 그 화면을 보고 쓸 수 있는가"는
검증되지 않은 채 남는다. 테스트는 텍스트로 요소를 찾아 클릭하고, 리뷰는 공통 클래스가
붙었는지 본다. 둘 다 통과해도 버튼이 일반 텍스트처럼 보여 아무도 누르지 않을 수 있다.
이 계약은 그 틈을 **실제 렌더링과 조작**으로 메운다.

판정 근거는 렌더링된 화면과 조작 결과다. 코드, 클래스, 토큰, 테스트 통과, 스크린샷
파일의 존재는 단서일 뿐 근거가 아니다.

## 적용 범위

- **적용한다**: 화면 마크업·스타일·템플릿, 사용자에게 보이는 문구, 조작 요소의 동작
  (펼침·제출·이동·확인 다이얼로그), 화면에 드러나는 오류·빈 상태·권한 분기가 바뀐 변경.
  서버가 HTML을 렌더링하는 화면(Flask/Jinja, Django, Thymeleaf, JSP, ERB, Blade 등)도 같다.
- **적용하지 않는다**: 화면에 드러나지 않는 API·배치·스키마·내부 리팩터링. 판단이
  애매하면 "이 변경 뒤에 사용자가 보거나 누르는 것이 달라지는가"로 정한다.

## 무엇이 우선하는가

1. 프로젝트 규칙: `AGENTS.md`, `.ai-harness/docs/ui.md`(앱 실행·로그인·지원 뷰포트·테마·
   기준 화면), 프로젝트의 디자인 문서, 의미 토큰, 공통 컴포넌트, 기준 화면(디자인 시스템
   예시 페이지)
2. 이 계약과 [검토 체크리스트](references/checklist.md)
3. 외부 디자인 스킬(설치돼 있을 때만, 선택 보조). 썼다면 이름과 버전을 보고서에 남긴다.
   외부 스킬의 검사 통과는 "금지 항목이 측정되지 않았다"는 뜻일 뿐 이 계약의 근거를
   대신하지 않는다. 프로젝트 규칙과 부딪히면 프로젝트 규칙을 따른다.

이 계약은 특정 디자인 스킬, 점수 체계, 에이전트 구성을 강제하지 않는다.

## 작성과 검토를 나눈다

화면을 만들거나 고친 쪽(작성)과 판정하는 쪽(검토)을 구분한다. 같은 에이전트가 둘 다
하더라도 검토 단계에서는 작성 의도나 "고쳤다"는 설명이 아니라 지금 렌더링된 화면으로만
판정한다.

- 검토는 **작업 트리를 바꾸지 않는다.** 앱을 띄우고, 브라우저로 열고, 조작하고, 캡처한다.
  캡처와 기록은 저장소 밖(러너가 준 증거 경로, 없으면 임시 디렉터리)에 둔다.
- 앱은 프로젝트가 문서화한 로컬·테스트 설정으로 띄운다. 운영 계정·시크릿을 쓰지 않는다. 검토는
  아직 사람이 리뷰하지 않은 코드를 실행하는 일이다. 앱이 쓰는 DB 파일·업로드·로그·브라우저
  프로필도 저장소 밖으로 보낸다.
- 검토가 찾은 주요 문제는 작성 쪽(repair)이 고친다. 고친 뒤에는 같은 검토를 다시 돈다.

## 단계

### 1. 요청 분석

- 이 화면을 쓰는 **사용자 역할**과 그 역할이 가진 권한
- **진입 → 핵심 행동 → 성공 확인 → 복귀** 흐름. 예: 승인 대기 목록 진입 → 반려 사유 입력 후
  반려 → 반려됨 표시 확인 → 목록으로 돌아와 다음 건 처리
- 필요한 **상태**: 기본(접힌 상태 포함), 비어 있음, 로딩, 오류, 권한 없음, 긴 텍스트, 처리 완료
- 위를 **검증 시나리오** 목록으로 만든다. 시나리오마다 뷰포트(데스크톱·모바일)와
  지원 테마를 정한다

산출물: 시나리오 목록. 워크플로 안에서는 brief의 `ui_scenarios`가 이것이다.

### 2. 디자인 시스템 확인

구현이나 검토 전에 프로젝트에 이미 있는 것을 찾는다.

- 디자인 문서, 의미 토큰(색·간격·타이포의 역할 이름), 공통 컴포넌트(버튼·disclosure·
  다이얼로그·폼 필드), 기준 화면
- 바꾸려는 화면과 **같은 역할을 하는 이웃 화면**: 같은 종류의 행동을 어떤 컴포넌트·문구·
  배치로 처리하는지

산출물: 이 변경이 따라야 할 컴포넌트·토큰·이웃 화면 목록.

### 3. 디자인 시스템 검토 (구현 후)

diff를 읽고, 그다음 **렌더링된 화면**을 본다.

- 같은 역할의 공통 컴포넌트가 있는데 일회성 마크업·스타일로 만들었는가
- 토큰 대신 하드코딩한 값, 이웃 화면과 다른 용어·배치·저장 방식이 있는가
- 공통 컴포넌트를 썼어도 **전역 CSS나 화면 CSS가 그 모양을 덮어쓰지 않았는가**
  (렌더링 결과로 확인한다. 클래스가 붙었다는 사실로 통과시키지 않는다)

### 4. 사용자 UX 검토 (실제 조작)

시나리오를 브라우저에서 **처음 보는 사용자처럼** 따라간다.

- 기본 상태(hover·focus 없음) 캡처만 보고 버튼·링크·펼침 요소를 조작 요소로 알아볼 수 있는가
- 펼침 요소에 펼칠 수 있다는 표시와 펼친 상태 표시가 있는가
- 행동 이름만 읽고 결과를 예측할 수 있는가. 실제 결과가 그 이름과 같은가
- 필수 입력이 표시되는가. 비우거나 틀리게 제출하면 무엇이 왜 틀렸고 어떻게 고치는지 보이는가.
  입력값이 남아 있는가
- 되돌리기 어려운 행동(반려·삭제·승인 등)에 확인이나 실행 취소가 있는가
- 키보드만으로 시나리오를 끝낼 수 있는가. 포커스가 보이고, 펼침·다이얼로그가 포커스를
  올바르게 옮기는가
- 모바일 폭에서 실제로 탭해서 끝낼 수 있는가. 가로 넘침·잘림·가림이 없는가
- 지원하는 테마마다 각각 렌더링했는가

세부 항목은 [체크리스트](references/checklist.md)를 따른다. 프로젝트에 없는 상태·테마는 건너뛰되
건너뛴 이유를 적는다.

### 5. 수정과 재검증

- 주요 문제를 고친다. 이웃 화면과 맞추는 수정이면 공통 컴포넌트를 재사용한다
- 고친 뒤 **영향받은 시나리오를 다시 실행**한다. 처음 문제를 찾은 상태(기본·접힘·모바일 등)부터
  다시 본다
- 기준 화면(디자인 시스템 예시)을 추가하거나 바꿨다면 **그 예시도 실제로 열고 조작한다.**
  예시가 코드에 있다는 것만으로는 기준 화면의 CSS가 예시를 가리는 문제를 찾을 수 없다

### 6. 근거와 한계 보고

시나리오마다 아래를 남긴다.

| 항목 | 내용 |
|---|---|
| 화면·시나리오 | 경로(URL), 역할, 진입 → 행동 → 확인 → 복귀 |
| 환경 | 뷰포트, 테마, 브라우저 도구, 데이터 조건 |
| 조작 | 실제로 누르고 입력한 순서 (마우스·키보드·탭) |
| 캡처 | 기본 상태와 각 단계의 캡처 경로 |
| 발견 | 주요 / 비주요, 근거(무엇을 보고 판정했는가) |
| 수정·재검증 | 무엇을 고쳤고 어떤 시나리오를 다시 돌렸는가 |
| 미해결·미검증 | 남은 문제, 확인하지 못한 시나리오·뷰포트·테마와 그 이유 |

외부 디자인 스킬을 썼다면 이름·버전과 그 결과를 따로 적는다.

## 판정

| 판정 | 조건 |
|---|---|
| `verified` | 모든 시나리오를 렌더링·조작했고 주요 문제가 없다 |
| `issues` | 주요 문제가 하나 이상 있다. 수정과 재검증으로 간다 |
| `unverified` | 앱을 띄우지 못했거나, 브라우저를 쓸 수 없었거나, 필수 시나리오·뷰포트·테마 중 하나라도 실제로 확인하지 못했다 |

**`unverified`는 완료가 아니다.** "구현 완료, 화면 검증 미완료"로 구분해서 보고하고 무엇이
막혔는지 적는다. 주요 문제가 남은 채로도 완료라고 하지 않는다.

**주요 문제**는 사용자가 핵심 행동을 찾지 못하거나 잘못 이해하는 것, 행동 이름과 결과가
다른 것, 필수 입력이나 오류에서 복구할 수 없는 것, 키보드나 지원 뷰포트·테마에서 시나리오를
끝낼 수 없는 것, 같은 역할의 공통 컴포넌트를 두고 일회성으로 만든 것, 되돌리기 어려운 행동에
확인이 없는 것이다. 간격·정렬처럼 시나리오 완주에 영향이 없는 것은 비주요로 남긴다.

## 거짓 통과

아래는 모두 **통과 근거가 아니다.** 검토 보고에 이것만 있으면 `unverified`다.

| 겉보기 근거 | 놓치는 것 | 대신 확인할 것 |
|---|---|---|
| 브라우저 테스트가 텍스트로 요소를 찾아 클릭하고 결과를 확인했다 | 사람이 그 요소를 누를 수 있는 것으로 알아보는가 | 기본 상태 캡처만 보고 조작 요소를 짚을 수 있는가 |
| 공통 버튼 클래스·의미 토큰이 마크업에 있다 | 전역·화면 CSS가 그 모양을 덮어썼는가 | 렌더링된 모양이 이웃 화면의 같은 컴포넌트와 같은가 |
| `<details>`/`<summary>`로 접근성 있는 disclosure를 만들었다 | 전역 CSS가 펼침 마커를 숨겨 일반 텍스트처럼 보이는가 | 접힌 기본 상태에서 펼칠 수 있다는 표시가 보이는가 |
| 스크린샷 파일이 있다 | 어떤 상태·뷰포트·테마를 찍었는가, 문제가 보이는 상태를 찍었는가 | 시나리오별 기본 상태와 각 단계 캡처가 있는가 |
| 디자인 시스템 기준 화면에 예시 코드를 추가했다 | 기준 화면의 CSS가 예시를 가리거나 비활성처럼 보이게 하는가 | 기준 화면을 열고 예시를 실제로 조작했는가 |
| `data-theme`, `aria-expanded` 같은 속성이 설정됐다 | 그 속성으로 화면이 실제로 바뀌는가 | 테마·상태마다 렌더링 결과를 따로 봤는가 |
| 검토 기록 파일·코드 해시·테스트 성공을 게이트가 확인했다 | 게이트는 증거가 있고 최신인지만 본다 | 위 항목들을 사람이나 검토 노드가 실제로 판정했는가 |
| "수정했다"는 설명 | 수정 뒤 화면이 실제로 달라졌는가 | 수정 뒤 같은 상태에서 다시 찍은 캡처 |

## 자동 게이트의 한계

워크플로의 게이트(러너, 해시, 검토 기록 확인)는 **증거가 있고 지금 작업 트리에 대한
것인지**만 확인한다. 화면이 보기 좋은지, 사용자가 알아보는지는 판정하지 못한다. 게이트를
통과했다는 사실을 시각·사용성 적합성으로 보고하지 않는다.
