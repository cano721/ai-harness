# UI 검토 체크리스트

업무 화면(관리자·승인·설정·목록·폼) 기준이다. 항목마다 **렌더링된 화면에서 무엇을 보면
되는지**를 적었다. 프로젝트에 해당 상태·테마·뷰포트가 없으면 건너뛰고 이유를 남긴다.
수치는 WCAG 2.2가 출처이고, 프로젝트 문서가 더 엄격하면 프로젝트 문서를 따른다.

## 발견 가능성

1. **기본 상태로 식별** — hover·focus 없이 찍은 캡처만 보고 버튼·링크·펼침 요소를 모두
   짚을 수 있다. hover해야 조작 요소인지 알 수 있으면 주요 문제다.
2. **펼침 표시** — 접힌 요소(`<details>`, 아코디언, "더보기")에 펼칠 수 있다는 표시가 보이고,
   펼친 뒤에는 펼친 상태가 시각적으로나 보조기술(`aria-expanded` 등)로 드러난다.
3. **핵심 행동의 위치** — 그 화면에서 가장 자주 하는 행동이 메뉴나 접힘 뒤에 숨지 않았다.
   숨겼다면 한 번 조작으로 닿는다.
4. **입력란이 입력란으로 보인다** — 테두리·배경·라벨로 일반 텍스트와 구분된다.

## 일관성

5. **같은 역할, 같은 모양** — 같은 종류의 행동(주 행동·보조 행동·위험 행동)이 이웃 화면과
   같은 컴포넌트·크기·위치를 쓴다.
6. **일회성 구현 없음** — 공통 컴포넌트·의미 토큰이 있는 역할을 직접 만든 마크업이나 하드코딩
   값으로 처리하지 않았다. 공통 컴포넌트를 썼어도 화면 CSS가 모양을 덮어쓰지 않았다.
7. **용어와 저장 방식** — 이웃 화면과 같은 용어를 쓰고, 저장(즉시 반영·저장 버튼·자동 저장)
   방식이 같다.
8. **기준 화면이 살아 있다** — 디자인 시스템 예시·기준 화면이 현재 CSS로 렌더링되고, 예시의
   조작 요소를 실제로 누를 수 있다.

## 상태

9. **조작 요소의 상태** — 기본·hover·focus·눌림·비활성·처리 중·오류가 서로 구분된다.
10. **비활성과 읽기 전용 구분** — 누를 수 없는 것(비활성)과 볼 수만 있는 것(읽기 전용)이
    다르게 보이고, 활성 요소가 비활성처럼 보이지 않는다.
11. **색만으로 상태를 전하지 않는다** — 선택·오류·성공·배지 상태가 색 말고도 텍스트·아이콘·모양
    중 하나로 구분된다(SC 1.4.1). 흑백으로 봐도 상태를 읽을 수 있어야 한다.
12. **빈 상태는 이유별로 다르다** — 첫 사용(아직 만든 것이 없음 → 만드는 행동), 검색 결과 없음(검색어
    고치기), 필터 결과 없음(필터 해제), 권한 없음(누구에게 요청하는지), 불러오기 실패(다시 시도)를
    구분해서 말한다. 실패를 "데이터가 없습니다"로 보여 주지 않는다.
13. **로딩과 긴 텍스트** — 로딩 중 레이아웃이 튀지 않고, 로딩 문구는 "불러오는 중"보다 실제 작업
    이름("승인 대기 목록을 불러오는 중")을 쓴다. 실제 진행을 모르면 진행률·남은 시간을 지어내지 않는다.
    긴 이름·금액이 잘리거나 겹치지 않는다.

## 행동과 결과

14. **이름이 결과를 말한다** — 버튼 문구만 읽고 무엇이 일어날지 예측할 수 있고, 실제 결과가
    같다. 확인 다이얼로그의 버튼은 "확인/취소"보다 실제 행동(예: "반려", "닫기")을 쓴다.
15. **되돌리기 어려운 행동** — 반려·삭제·승인·발송은 확인이나 실행 취소가 있고, 위험 행동은
    색과 위치로 일반 행동과 떨어져 있다.
16. **처리 중과 완료** — 제출 중 다시 누를 수 없고, 끝나면 성공했다는 것이 화면에 보인다.
17. **상태 변화를 보조기술도 듣는다** — 저장 완료·오류·결과 건수처럼 포커스를 옮기지 않는 상태
    변화는 `role="status"`·`aria-live` 영역으로 알린다(SC 4.1.3). 자동으로 사라지는 알림은 정보성일
    때만 쓰고, 행동(실행 취소·다시 시도)을 담은 알림은 사용자가 닫을 때까지 남거나 hover·focus 중에
    멈춘다.
18. **복귀** — 완료 뒤 돌아가는 위치가 예측 가능하고, 목록의 필터·페이지·스크롤이 유지된다.
    뒤로가기·새로고침에서 중복 제출이나 데이터 손실이 없다.
19. **드래그에 대안이 있다** — 끌어서 놓기·슬라이더·순서 바꾸기는 한 번 누르기(버튼·메뉴·입력)로도
    할 수 있다(SC 2.5.7). 끄는 도중 취소할 수 있다.

## 입력과 오류

20. **필수 입력** — 필수 항목이 제출 전에 표시되고, placeholder만으로 라벨을 대신하지 않는다.
21. **입력 효율** — 입력란에 맞는 `type`(email·tel·number·date)과 `autocomplete`, 숫자 키패드가 필요한
    곳에 `inputmode`를 쓴다. 형식 검증은 입력하는 도중이 아니라 입력란을 떠날 때(blur)나 제출할 때
    한다. 이미 받은 값을 다시 입력하게 하지 않는다(SC 3.3.7).
22. **오류 위치와 문구** — 오류가 해당 필드나 실패한 영역 옆에 나오고, 무엇이·왜 틀렸고·지금
    무엇을 하면 되는지 말한다. 필드 오류는 `aria-describedby`로 그 입력란에 연결되고 `aria-invalid`가
    설정된다.
23. **복구** — 제출이 실패해도 입력값이 남아 있고, 포커스가 첫 오류나 오류 요약으로 간다.
    서버 오류에는 다시 시도할 길이 있다.
24. **실패 원인별 안내** — 401(로그인이 끝남 → 다시 로그인 후 원래 화면으로), 403(권한 없음 → 누구에게
    요청하는지), 404(없거나 지워짐 → 목록으로), 429(요청이 많음 → 잠시 후, 알면 기다릴 시간), 500(서버
    오류 → 다시 시도와 문의 경로), 오프라인(연결 끊김 → 입력 보존과 다시 시도)을 한 문구로 뭉치지 않는다.

## 키보드·모바일·테마

25. **키보드로 완주** — Tab·Enter·Space·Esc만으로 시나리오를 끝낸다. 포커스가 항상 보이고,
    고정 헤더 등에 가려지지 않는다(SC 2.4.11).
26. **포커스 이동** — 펼침·다이얼로그를 열면 포커스가 안으로 들어가고, 닫으면 연 요소로
    돌아온다. 다이얼로그는 Esc로 닫힌다.
27. **잘림과 가림** — 드롭다운·팝오버·툴팁이 스크롤 영역이나 `overflow` 조상에 잘리지 않는다.
28. **모바일 폭** — 390px 안팎에서 실제로 탭해서 시나리오를 끝낸다. 가로 스크롤이 생기지 않으며,
    hover에만 기대는 정보가 없다.
29. **터치 영역** — 누르는 대상은 24×24 CSS px 이상이거나, 작으면 이웃 대상과 중심 간격이 24px
    이상이다(SC 2.5.8). 이보다 작으면 주요 문제다. 주 행동과 모바일 화면의 대상은 44×44 CSS px를
    권장하고(SC 2.5.5), 24px 이상 44px 미만은 비주요로 남긴다.
30. **확대와 리플로** — 브라우저 확대 200%에서 글자가 잘리거나 겹치지 않고 기능이 모두 남는다
    (SC 1.4.4). 폭 320 CSS px(1280px 화면의 400% 확대에 해당)에서 표·코드처럼 2차원 배치가 필요한
    것을 빼고는 가로 스크롤 없이 한 방향으로 읽힌다(SC 1.4.10).
31. **대비** — 본문 글자는 배경과 4.5:1 이상, 큰 글자(24px 이상, 굵게면 18.66px 이상)는 3:1 이상이다
    (SC 1.4.3). 입력란 테두리·아이콘 버튼·체크 표시 같은 UI 구성 요소와 포커스 표시는 인접 색과
    3:1 이상이다(SC 1.4.11). 비활성 요소는 예외지만 활성 요소가 그 대비로 보이면 10번 문제다.
32. **테마** — 지원하는 테마(라이트·다크·고대비)마다 따로 렌더링해서 31번 대비와 상태 구분을
    확인한다. 한 테마 결과로 다른 테마를 추정하지 않는다.

## 모션

33. **감소 모션을 실제로 렌더링한다** — OS나 브라우저 도구로 `prefers-reduced-motion: reduce`를 켜고
    같은 시나리오를 다시 본다. 이동·확대·패럴랙스는 사라지거나 즉시 바뀌고, 상태를 알려 주는
    opacity·색 변화와 눌림·처리 중 피드백은 남는다. 모든 전환을 한꺼번에 끄는 구현은 기능이 남아 있으면
    비주요다. 감소 모션에서 콘텐츠가 보이지 않거나 조작할 수 없으면 주요 문제다.
34. **전환이 다음 조작을 막지 않는다** — 열림·닫힘·목록 전환 중에도 다음 클릭·입력·Esc가 먹고, 전환이
    끝날 때까지 기다리게 하지 않는다. 막으면 주요, 길기만 하고 막지 않으면 비주요다.
35. **반복 애니메이션을 멈춘다** — 5초를 넘게 도는 움직임(캐러셀·배너·로딩 외 장식)은 멈출 수 있고
    (SC 2.2.2), 화면 밖으로 나가거나 탭이 숨겨지면 멈춘다.
36. **깜빡임** — 1초에 3번을 넘게 번쩍이는 것이 없다(SC 2.3.1).
37. **기본 상태에서 콘텐츠가 보인다** — 등장 애니메이션이 실패하거나 스크립트가 늦어도 콘텐츠가
    처음부터 보인다. 등장 연출 때문에 빈 화면이나 투명한 요소가 남지 않는다.

## 검토 질문

판정 전에 스스로 묻는다.

- 코드를 보고 판정했는가, 렌더링을 보고 판정했는가?
- 이 캡처는 문제가 드러나는 상태(접힌 기본 상태, 모바일, 다른 테마, 감소 모션)를 찍었는가?
- 테스트가 요소를 찾았다는 것과 사람이 그것을 알아본다는 것을 같은 것으로 보지 않았는가?
- 속성·클래스가 설정됐다는 것과 화면이 바뀌었다는 것을 같은 것으로 보지 않았는가?
- 비교한 기준 화면 자체가 현재 CSS로 올바르게 보이는가?
- 수정 뒤 처음 문제를 찾은 상태에서 다시 확인했는가?
- 모바일·터치 결과가 뷰포트 에뮬레이션·합성 터치·실기기 중 무엇에서 나왔는지 적었는가?
- 확인하지 못한 시나리오·뷰포트·테마를 보고서에 적었는가?
