# 테스트 결정 규약

작성법이 아니라 **결정**을 담는다. `getByRole`을 왜 먼저 쓰는지, `findBy*`와
`waitFor`가 어떻게 다른지는 [Testing Library 문서](https://testing-library.com/docs/queries/about/#priority)가
더 정확하고 최신이다. 여기 옮겨 적으면 버전이 올라갈 때 조용히 틀린 문서가
된다.

프로젝트에 테스트 정책이 있으면(`AGENTS.md`, `.ai-harness/workflows/`,
`.ai-harness/docs/`) 그쪽이 우선한다. 아래는 그 정책이 없을 때의 기본값이고,
CI가 실제로 무엇을 잡는지(타입 검사·린트·시각 회귀 유무)는 결정 전에
저장소에서 확인한다.

## 언제 여는가 — 그리고 테스트를 먼저 쓸 것인가

이 스킬은 **테스트 파일을 열 때가 아니라 기능 코드를 시작할 때** 본다. 제일
값나가는 건 결정 1(쓸 것인가)인데, 테스트 파일을 만든 시점엔 이미 그 답을
내린 뒤라 늦다.

작성 순서는 하나로 정하지 않는다. 결정 2의 사다리를 그대로 따라간다.

| 층위 | 순서 | 왜 |
|---|---|---|
| 순수 함수 (유틸·도메인 변환) | **테스트 먼저** | 입출력이 구현 전에 정해진다. TDD가 제값 하는 유일한 자리다 |
| 컴포넌트 | **구현 먼저** | 마크업이 굳기 전에 쓴 `getByRole` 쿼리는 어차피 다시 쓴다. 상상한 역할·라벨에 맞춰 테스트를 쓰면 구현이 테스트를 따라가게 되고, 그게 결정 4가 말하는 "지워야 할 테스트"다 |
| 페이지 통합 | 구현 먼저 | 조립이 끝나야 시나리오가 보인다 |
| **버그 수정** | **항상 테스트 먼저** | 실패하는 테스트가 곧 재현이고, 통과가 수정의 증거다 |

> **모든 기능에 구현 전 테스트를 요구하는 TDD 지침보다 이 표가 우선한다.**
> React 컴포넌트에서는 위 이유로 역효과가 난다. 순수 함수와 버그 수정에서는
> 두 지침이 어차피 같은 말을 한다.

## 결정 1 — 이 변경에 테스트를 쓸 것인가

**질문 하나: 이게 틀렸을 때 누가 먼저 알아채는가?**

| 먼저 알아채는 것 | 판단 |
|---|---|
| 타입 검사 (타입 불일치, 빠진 prop) | 쓰지 않는다. CI가 이미 잡는다 |
| 린터 | 쓰지 않는다 |
| 시각 회귀 도구 (스냅샷/Chromatic 등) | 쓰지 않는다. 시각 회귀는 저기 담당이다 |
| **아무도 없음 — 사람이 클릭해봐야 안다** | **쓴다** |

마지막 칸이면 쓴다. 그게 전부다.

여기에 무조건 규칙 하나만 더 붙는다: **버그를 고칠 때는 항상 테스트를 먼저
쓴다.** 그 버그가 이미 "아무도 못 잡았다"는 걸 증명했기 때문이다. 재발
방지가 아니라 수정이 실제로 그 버그를 고쳤다는 증거로 필요하다.

반대로 이런 이유로는 쓰지 않는다 — "커버리지가 낮아서", "PR에 테스트가 있으면
보기 좋아서", "나중에 누가 고칠까 봐". 마지막 것이 제일 위험하다. 근거 없는
불안으로 쓴 테스트는 구현 세부에 붙고, 그게 §결정 4의 "지워야 할 테스트"가
된다.

## 결정 2 — 어느 층위인가

위에서부터 내려오다 **처음 걸리는 칸에서 멈춘다.** 아래로 더 내려가지 않는다.

1. **타입으로 표현되는가** → 타입으로 끝낸다. 테스트 없음
   *(예: 아이콘 이름 유니온이 오타를 컴파일 에러로 막는 것)*
2. **순수 함수로 뽑을 수 있는가** → 그 함수만 단위 테스트한다. 컴포넌트는 안 건드린다
   *(날짜 포맷, 필터 조건 조립, 범위 계산)*
3. **사용자 조작 → 화면 변화인가** → 컴포넌트 테스트 (RTL + jsdom)
   *(체크박스를 켜면 선택 개수가 바뀐다)*
4. **여러 모듈이 엮여야 드러나는가** → 페이지 통합 테스트. **페이지당 하나**
   *(목록을 열면 API를 부르고 결과가 표로 나온다)*
5. **눈에 보이는 모양인가** → 스토리 + 시각 회귀. 테스트 파일 없음

**한 동작은 한 층위에서만 검증한다.** 같은 필터 로직을 단위로도, 컴포넌트로도,
통합으로도 확인하면 리팩터링 때 세 곳이 동시에 깨진다. 3번을 썼으면 그 안의
계산을 2번으로 또 확인하지 않는다.

층위가 올라갈수록 개수를 줄인다. 단위는 많아도 되고, 페이지 통합은 페이지당
하나가 상한이다.

## 결정 3 — 어느 레이어에 두는가

레이어별 테스트 밀도가 다르다. 아래는 [Feature-Sliced Design](https://feature-sliced.design/)
기준이며(`feature-sliced-design` 스킬 참조), 다른 구조라면 "공용 로직 / 도메인
모델 / 사용자 시나리오 / 화면 조립 / 앱 배선"으로 대응시켜 읽는다.

| 레이어 | 테스트 밀도 | 무엇을 |
|---|---|---|
| `shared/lib`, `shared/api` | **높음** | 순수 함수·클라이언트. 여기가 단위 테스트의 본진 |
| `entities` | 낮음 | 도메인 변환 함수만. 엔티티 UI는 표현용이라 안 쓴다 |
| `features` | **높음** | 사용자 시나리오 하나 = 테스트 하나. 컴포넌트 테스트의 본진 |
| `pages` | 페이지당 1개 | 조립이 되는지 보는 통합 스모크. 그 이상 쓰지 않는다 |
| `app` | 없음 | 프로바이더 배선. 앱이 뜨면 증명된다 |

파일은 **대상 바로 옆에** `*.test.ts(x)`로 둔다. `__tests__/` 디렉터리를 만들지
않는다 — 함께 수정되는 파일은 같은 곳에 있어야 한다(응집도).

재export와 설정 객체뿐인 패키지는 테스트할 런타임 로직이 없다. 거기에 `test`
스크립트가 없는 건 실수가 아니라 결정일 수 있으니, 없앤 이유를 확인하기 전에
추가하지 않는다. 타입 검사와 빌드가 그 자리를 커버한다. 다만 워크스페이스
전체 실행(`pnpm -r test` 등)은 스크립트가 없는 패키지를 **조용히 건너뛴다** —
직접 쓴 로직이 생기면 그때 스크립트를 추가한다.

## 결정 4 — 깨진 테스트를 고칠 것인가 지울 것인가

**질문: 테스트를 고치려고 손대는 부분이 사용자에게 보이는가?**

- **보인다** (버튼 텍스트, 역할, 상태, 흐름이 바뀌었다) → 의도된 변경이다.
  테스트를 새 동작에 맞춘다
- **안 보인다** (내부 구조, 컴포넌트 분리, DOM 계층, 훅 이름이 바뀌었을 뿐인데
  깨졌다) → **테스트가 잘못 쓰인 것이다.** 통과하게 고치지 말고, 사용자
  관점으로 다시 쓰거나 지운다. 여기서 "일단 통과시키자"를 하면 그 테스트는
  다음 리팩터링에서 또 깨지고, 결국 아무도 안 믿는 테스트가 된다
- **간헐적으로 깨진다** → 대기 문제다. `waitFor` 타임아웃을 늘리는 건
  해결이 아니라 은폐다. `findBy*`로 바꾸고, 그래도 흔들리면 지운다.
  **신뢰할 수 없는 테스트는 없는 것보다 나쁘다** — 빨간불을 무시하는 습관을
  만든다

## 결정 5 — 커버리지 목표를 둘 것인가

**두지 않는다.** 커버리지는 "그 줄이 실행됐다"를 재지 "그 동작이 검증됐다"를
재지 않는다. 단언 없이 렌더만 해도 숫자는 올라간다. 재export 비중이 큰
저장소에서는 특히 의미가 없다.

대신 이 트리거를 쓴다: **같은 파일에서 버그가 두 번 나면 그 파일에 테스트를
쓴다.** 숫자보다 이쪽이 실제 위험 지점을 가리킨다.

## 아직 없는 도구 — 도입 시점

저장소에 없는 도구는 트리거가 실제로 발생했을 때 넣는다.

### Vitest 브라우저 모드

Vitest 4에서 정식이 됐다. 하지만 **jsdom을 전부 이사시키는 게 아니라 2트랙**이다.
로직·조건부 렌더·폼은 jsdom에 남기고, 아래만 브라우저로 보낸다.

**트리거**: "jsdom이 이 API를 구현하지 않아서 테스트를 못 쓴다"가 처음 발생한
순간. 실제 레이아웃(`getBoundingClientRect`), 포커스 트랩, 팝오버 위치,
`IntersectionObserver`, 드래그, 클립보드. 그 전에 CI에 브라우저를 붙이면
파이프라인만 몇 배 느려진다.

```bash
# 패키지 매니저·워크스페이스 필터는 저장소에 맞춘다
npm i -D @vitest/browser-playwright vitest-browser-react playwright
```

```ts
// v4에서 provider가 문자열이 아니라 함수다 — 옛 예제를 복사하면 깨진다
import { playwright } from "@vitest/browser-playwright";
test: { browser: { provider: playwright(), enabled: true, instances: [{ browser: "chromium" }] } }
```

API가 통째로 갈린다: `render`는 `vitest-browser-react`에서, `screen` 대신
`page`, `expect(el)` 대신 `await expect.element(el)`, `userEvent`는
`vitest/browser`에서(시뮬레이션이 아니라 CDP 실제 입력이라 Testing Library
공식 문서조차 이쪽을 권한다).
[vitest.dev/guide/browser](https://vitest.dev/guide/browser/)

시각 회귀용 `toMatchScreenshot()`도 여기 있다. **이미 시각 회귀 도구가 있으면
겹쳐 넣지 않는다.**

### Storybook `addon-vitest`

스토리를 브라우저 모드 테스트로 바꿔주는 애드온이다. 스토리가 표현용
재export뿐이고 시각 회귀를 별도 도구가 커버하고 있으면 **지금 넣지 않는다.**

**도입 트리거**: `play` 함수가 필요한 — 상호작용을 가진 — 우리 컴포넌트가
생겼을 때. 그때는 스토리 재활용이 별도 테스트 파일보다 싸다.

## 자주 틀리는 지점

공식 문서와 어긋나거나, 문서에 있어도 반복해서 놓치는 것만.

1. **`globals: true`는 사실상 필수다.** Testing Library의 자동 `cleanup`이 전역
   `afterEach`에 붙는다. 끄면 테스트 간 DOM이 샌다
2. **디자인 시스템이 Provider를 요구하면 그 안에서 렌더한다.** 테마 토큰이
   없으면 렌더가 깨진다. 한 앱에서 세 번 이상 반복되면 그때 `renderWithTheme`을
   공용 위치에 만든다 — 두 번까지는 복붙이 낫다
3. **클래스명으로 조회·단언하지 않는다.** CSS Modules는 해시되므로 애초에
   동작하지 않는다. 역할과 텍스트로 조회한다
4. **단언은 jest-dom matcher로 한다.** setup 파일에서 등록한다.
   `getBy*`는 못 찾으면 던지므로 `toBeTruthy()`는 아무것도 검증하지 않는
   장식이다 → `toBeInTheDocument()`
5. **인터랙션은 `user-event`로 한다.** `fireEvent`는 쓰지 않는다 — DOM 이벤트
   하나만 던지므로 실제 클릭이 일으키는 포인터·포커스 연쇄를 재현하지 못하고,
   그래서 `disabled` 버튼도 눌린 것처럼 통과시킨다

   ```tsx
   const user = userEvent.setup();          // 반드시 render 전에
   render(
     <ThemeProvider theme={theme}>
       <JobFilter />
     </ThemeProvider>,
   );
   await user.click(screen.getByRole("checkbox", { name: "정규직" }));
   ```

   모든 호출에 `await`를 붙인다. 빼먹으면 단언이 상태 갱신보다 먼저 돌아서
   실패하고, React 19의 `act` 경고로 나타난다 — 그 경고는 `act()`로 감싸라는
   뜻이 아니라 **`await`를 빠뜨렸다는 신호다.**

   이 패키지는 14.6.4에서 사실상 동결됐다. jsdom에서는 여전히 최선이지만,
   브라우저 모드로 가면 `vitest/browser`의 `userEvent`로 갈아탄다(위)

코드 품질 점검은 `frontend-fundamentals`, `useEffect` 판단은
`no-unnecessary-effects` 스킬이 따로 있다. 여기서 중복하지 않는다.
