# Frontend Fundamentals 코드 품질 리뷰

Toss Frontend Fundamentals의 4가지 원칙에 따라 프론트엔드 코드를 분석하고 개선안을 제시한다.

> 좋은 코드란 **"변경하기 쉬운 코드"**이다.

## 리뷰 대상

`$ARGUMENTS`가 제공되면 해당 파일/디렉토리를 분석한다. 없으면 최근 변경된 파일(git diff)을 대상으로 한다.

## 리뷰 절차

### 1단계: 코드 읽기
- 대상 파일을 읽고 전체 구조를 파악한다
- 컴포넌트, Hook, 유틸리티 함수의 역할과 관계를 이해한다

### 2단계: 4가지 원칙으로 분석

각 원칙별로 코드 냄새를 점검한다. 상세 기준은 참조 문서를 확인한다:
- [가독성 가이드](references/readability.md)
- [예측 가능성 가이드](references/predictability.md)
- [응집도 가이드](references/cohesion.md)
- [결합도 가이드](references/coupling.md)
- [커뮤니티 합의 사항](references/community-consensus.md)

#### 가독성 (Readability) 체크리스트
- [ ] 동시에 실행되지 않는 코드가 한 컴포넌트에 섞여 있지 않은가?
- [ ] 한 번에 고려해야 할 맥락이 6~7개를 초과하지 않는가?
- [ ] 하나의 Hook이 너무 많은 쿼리 파라미터/상태를 관리하지 않는가?
- [ ] 복잡한 조건식에 의미 있는 이름이 붙어 있는가?
- [ ] 매직 넘버가 상수로 선언되어 있는가?
- [ ] 코드를 위에서 아래로 읽을 수 있는가? (시점 이동이 적은가?)
- [ ] 중첩 삼항 연산자가 if문으로 풀어져 있는가?
- [ ] 비교 순서가 왼쪽→오른쪽으로 자연스러운가? (`80 <= score && score <= 100`)

#### 예측 가능성 (Predictability) 체크리스트
- [ ] 같은 이름의 함수/변수가 동일한 동작을 하는가?
- [ ] 같은 종류의 함수가 동일한 반환 타입을 가지는가?
- [ ] 함수에 이름/파라미터/반환값으로 예측 불가능한 숨은 로직이 없는가?
- [ ] 불리언이 아닌 값을 조건식에 암묵적으로 사용하지 않는가?
- [ ] `enum` 대신 `as const`를 사용하고 있는가?

#### 응집도 (Cohesion) 체크리스트
- [ ] 함께 수정되는 파일이 같은 디렉토리에 있는가?
- [ ] 매직 넘버가 관련 코드와 함께 관리되는가?
- [ ] 폼의 응집도 방식(필드 단위 vs 폼 전체)이 상황에 맞게 선택되었는가?

#### 결합도 (Coupling) 체크리스트
- [ ] 하나의 Hook/컴포넌트가 하나의 책임만 가지는가?
- [ ] 향후 동작이 달라질 수 있는 코드를 무리하게 공통화하지 않았는가?
- [ ] Props Drilling이 3단계 이상 깊어지지 않았는가?
- [ ] Props Drilling 해결 시 순서를 따르고 있는가? (props 확인 → children → Context API)

### 3단계: 결과 출력

다음 형식으로 리뷰 결과를 출력한다:

```
## 코드 품질 리뷰 결과

### 요약
- 전체 평가: [좋음 / 개선 필요 / 주의 필요]
- 주요 발견: N건

### 발견 사항

#### [원칙] 제목
- **파일**: `path/to/file.tsx:L10-L25`
- **심각도**: [높음 / 중간 / 낮음]
- **현재 코드**: (문제가 되는 코드 발췌)
- **개선안**: (구체적인 코드 제안)
- **근거**: (어떤 원칙의 어떤 기준에 해당하는지)

### 트레이드오프 분석
- (이 코드에서 원칙 간 상충이 발생하는 지점을 반드시 1개 이상 서술한다)
- 형식: "**[원칙A] vs [원칙B]**: 설명 → 이 코드에서는 [원칙X]를 우선한 이유"
- 예시: "**응집도 vs 가독성**: 폼 검증 로직을 한 파일에 모으면 응집도는 높아지지만, 파일이 길어져 가독성이 떨어질 수 있다. 이 코드에서는 필드 간 의존성이 강하므로 응집도를 우선했다."

### 잘된 점
- (이미 원칙에 부합하는 코드가 있다면 언급)
```

## 주의사항

- **반드시 4가지 원칙(가독성, 예측 가능성, 응집도, 결합도) 모두에 대해 분석해야 한다.** 특정 원칙에 해당하는 문제가 없더라도, 해당 원칙이 잘 지켜지고 있다면 "잘된 점"에서 언급한다.
- 4가지 원칙은 상충할 수 있다. 현재 상황에서 **어떤 가치를 우선할지** 판단하여 제안한다.
- 응집도를 높이면 가독성이 떨어질 수 있고, 결합도를 낮추면 중복이 생길 수 있다.
- 모든 코드 냄새가 반드시 수정해야 하는 것은 아니다. 트레이드오프를 설명한다.
- 커뮤니티에서 합의된 패턴이 있는 경우 해당 근거를 함께 제시한다.
