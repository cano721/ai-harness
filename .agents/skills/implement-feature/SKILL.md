# Implement Feature

This is a project adapter, not the source of project policy. Read these files in order before planning or editing:

1. `AGENTS.md`
2. `.ai-harness/workflows/implement-feature.md`
3. `.ai-harness/workflows/feature-delivery-graph.json`
4. The personas and `.ai-harness/docs/` files selected by the workflow

The project workflow and graph are authoritative. They define the approval gate, test policy, role boundaries, validation commands, review/repair loop, and escalation conditions.

Start in planning mode and present the workflow-required implementation brief. Do not edit before explicit approval, or before the policy approval below when personal `HM_APPROVAL` is `auto`. After approval, follow the graph transitions and use configured project agents only for bounded responsibilities. A delegated agent must preserve the resolved personal delivery level: it takes precedence over “PR only, do not merge” in a delegation prompt and an instruction to stop at the PR does not override `HM_DELIVERY_LEVEL` or a matching `HM_DELIVERY_LEVEL_REPOS` entry. Delegate bounded work through the runner when the resolved level is `merge` or `deploy`.

## Project policy

Read `git_policy` (with the repository facts in `merge_policy`) and `issue_policy` from `.ai-harness/harness.json`. Read approval mode from `HM_APPROVAL` and `HM_APPROVAL_REPOS` in `~/.ai-harness/config`; a matching repository entry wins, then the global value, then `human`. Ignore legacy manifest `approval` and tell the user once to move it to personal settings. The runner picks the node runtime from `--runtime`, then `HM_RUNTIME_REPOS` (matching repository), then `HM_RUNTIME` in `~/.ai-harness/config`, then the calling CLI and integrations; pass `--runtime` only when the user asks for a specific CLI.

- `HM_APPROVAL`: `human` (default when no personal value is set) — present the brief and do not edit before explicit approval. `auto` — present the brief, record it in the PR body (the runner also keeps it in its run directory and records the setting source in state and `brief.md`), and continue without waiting. Instead of open questions, choose the recommended option wherever choices diverge and record each as a decision (question, choice, rationale) in a "결정 사항" section of the brief and the PR body, where the person can overturn it before merging. Wait for the person only for what they alone can decide: a product judgment that changes scope, a hard-to-reverse choice (deleting data, a migration, index changes, a deployment), or a write to an external system.
- `git_policy`: `pr-only` — once the graph reaches publish, commit, push the work branch with a normal push, and open a PR with the PR tool the project workflow names (for example /bitbucket or gh); take reviewers and labels from the project's default rules instead of asking. `direct` — commit and push the current branch with a normal push; open a PR only when the project workflow requires one. The older value `merge` is read as `pr-only`; the repository no longer decides merging. Resolve personal delivery level from `HM_DELIVERY_LEVEL_REPOS` (matching repository entry first), then `HM_DELIVERY_LEVEL` in `~/.ai-harness/config`. Without a value, or with `pr`, the run stops at the PR; `merge` or `deploy` must use the runner and let only its `merge` node merge after remote CI passes, into a base branch the host protects with required approvals, under the user's merge conditions (`HM_MERGE_*`), then run every post-merge check covered by that level using repository facts in `merge_policy` (base branch, deploy and smoke commands). The runner is mandatory for `merge` and `deploy`; if it is unavailable, do not substitute a manual merge or report completion: the first line must report the configured delivery level, its setting source, and why it could not be applied. `HM_INTERNAL_SESSION=1` runs never merge. `git_policy` sets only the commit and PR scope. Missing or any other value — do not commit, push, or create a PR unless separately authorized.
- Remote CI (the graph's `remote_ci` node): work that was pushed is not done until remote CI for the pushed commit has finished. Watch it with the PR or CI tool the project workflow names (for example `gh pr checks --watch`, or the Bitbucket pipelines API through /bitbucket) until every check reaches a final state. If it fails, repair it through the same loop and limit (`limits.max_repair_attempts`), push with a normal push, and check again. If the repository has no remote CI, say so. If you cannot see the result, report "remote CI unverified" with the PR link instead of done. A local run of the CI-equivalent commands does not stand in for remote CI.
- UI verification (the graph's `ui_review` node): when the change alters what users see or operate — markup, styles, server-rendered templates, user-facing text, or how buttons, links, disclosures, forms, and dialogs behave — the brief lists `ui_scenarios` (user role, entry → key action → success check → return, the states, viewports, and themes to see, and the mockup source — file, frame, or node — when a mockup exists). After a review with no blocking findings, verify them with the project `ui-review` skill (`.agents/skills/ui-review/SKILL.md` or `.claude/skills/ui-review/SKILL.md`) and `.ai-harness/docs/ui.md`: render and operate each scenario in a real browser without changing the working tree, keeping captures outside the repository. A blocking UI issue goes through repair, re-review, and `ui_review` again. If the screens could not be rendered or operated, report "implementation done, UI unverified" with what blocked it, never done. A test that clicked an element by its text, a class or token in the markup, or a screenshot file is not evidence.
- UI copy: when the change adds or changes interface text and `.ai-harness/docs/ux-writing.md` exists, read it before writing the copy and follow its glossary, ending style, and component rules. Before review, check the changed copy with `/ai-harness:ux-writing-audit` on the diff and fix its deterministic findings; report the score in the PR body. Without the document, do not invent project copy rules.
- `issue_policy`: `in-progress-on-start` — when the request names a tracker issue (a key such as `ABC-123` or an issue URL), move that issue to its in-progress state with the issue tool the project workflow names (for example /jira), before branch or worktree setup and before discovery. Pick the transition whose target status category is in progress instead of matching a status name. Leave an issue that is already in progress as it is; if it is done or closed, ask the person instead of reopening it. Do this before `driver.sh start` — the runner's first node is discovery. If the project workflow names no issue tool, ask the person which to use instead of guessing one. Missing or any other value — leave issue status alone.
- Under every policy: never merge, force-push, push to the base branch under `pr-only`, or change project policy without separate authorization — the only merge is the runner's `merge` node under a personal delivery level of `merge` or `deploy`. Unattended runs never merge. Escalations the graph routes to `user_decision`, such as the repair limit in `limits.max_repair_attempts` or a product decision, always go to the person.

## Graph runner

When `.ai-harness/workflows/workflow-driver.sh` exists, run the feature through it instead of following the graph yourself (`--workflow feature`; the older `implement-feature-driver.sh` forwards to it). The runner executes the graph outside the model: read-only nodes run in read-only sessions, the approval node waits for the person (or passes by policy under personal `HM_APPROVAL=auto`), done requires the checks the runner executes itself (the brief's fast checks before every review round, and its `final_checks` — the broad suite — once after a review finds nothing blocking), the ui_review node keeps its captures in the run directory, the publish node commits, pushes, and opens the PR only as `git_policy` allows, and the remote_ci node waits for remote CI on the pushed commit.

To stop a running run, use only `bash .ai-harness/workflows/workflow-driver.sh stop [--run <id>] [--reason "<why>"]`: it ends just the processes that run recorded (the runner and its node session group, TERM then KILL after 5 seconds) and records `stopped` with the node, time, and reason. Never kill the runner or agent sessions by pattern (`pkill`, `killall`, `pgrep -f`); the same pattern matches other runs and sessions on the machine. `status` shows a stopped run and a run cut off outside the runner (`stale`); continue either with `resume`. `resume`, `approve`, and `revise` refuse a run whose runner is still alive (exit 2).

1. `bash .ai-harness/workflows/workflow-driver.sh start --workflow feature --request "<the user's request>"` runs discover and brief, then stops at approval (exit 10). Show the brief, the checks, and any open questions to the user as printed. Under `HM_APPROVAL=auto` it does not stop unless the brief has open questions; go to step 4 when it exits. The brief maps every completion condition of the request and of any issue it quotes or links in `acceptance_map` (covered by an acceptance case or check, or out of scope with a reason); under `auto` the runner rewrites a brief whose map is empty or leaves a condition unmapped, and past `limits.max_brief_rewrites` hands it to a person through `brief_coverage_incomplete`.
2. If the user asks for changes, run `revise --workflow feature --feedback "<their words>"` and show the new brief. This also works during deliver (the graph's `deliver → brief` `brief_revised` edge): when the brief turns out to miss a condition, revise returns the run to the brief without killing it. If the runner is still running deliver, revise exits 0 and the runner goes back to the brief when that deliver session ends; the changes deliver made stay, and the new brief needs approval again.
3. When the user types `승인` or `approve`, run `resume --workflow feature`. The runner accepts only a message the user typed after the brief was shown, read from the session transcript. Never write, quote, or simulate an approval yourself. Delivery, checks, review, and repair can take many minutes; run it in the background when your tool allows it. While it runs, follow the file the runner prints after `progress:` on every start, resume, revise, and approve (one line per node transition and per tool call in Claude sessions) with a file monitor when your tool has one and pass new lines to the user as short progress notes. The user can watch the same lines in a terminal with `bash .ai-harness/workflows/workflow-driver.sh watch --workflow feature`.
4. Report the outcome: exit 0 done (with the PR link and the remote CI result when something was pushed, and when the runner merged, the merge commit and post-merge checks; a `notice:` about settings the runner no longer uses is passed on as is); 20 a person must decide (show the unresolved findings; a blocked merge or a failed post-merge check — the change stays merged and is not reverted — goes here; when remote CI is unverified, say so with the PR link and do not call the work done; when the UI is unverified, show the evidence directory it names. When the runner stopped because the repository changed since it stopped (`baseline-changes.txt`), show that file; run `resume --accept-changes` only when the user explicitly says to take those changes into the run, never on your own.); 30 incomplete (show the cause, then `resume` after it is fixed; when remote CI is still running, a merge condition is still unmet such as a missing approval, or the merge commit is not deployed yet, `resume` checks it again); 40 invariant violation (stop and show it). `status --workflow feature` shows the current node and history.

Under `pr-only` or `direct` the runner leaves a local checkpoint commit after delivery and each repair, and its publish node commits, pushes, and opens the PR; under any other `git_policy` it never commits. Branch or worktree setup before it and docs and cleanup after it follow the project workflow. In Codex, the runner starts its own sandboxed `codex exec` sessions, so run it with permission to leave the current sandbox. If the runner is missing, follow the graph in this conversation as described above.
